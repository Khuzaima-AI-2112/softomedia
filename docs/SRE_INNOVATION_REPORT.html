1. SHA-Based Versioning

The Concept: Binary Fingerprinting

Instead of the generic :latest tag, every image is tagged with a unique $BUILD_ID (or Git SHA). This acts as a permanent fingerprint for a specific state of the code.

Why It Matters

  • Atomic Rollbacks: If a new version crashes, we can instantly switch traffic back to the previous Build ID in Cloud Run without rebuilding.
  • Traceability: You can look at any running container and know exactly which Cloud Build event created it.
  • Parallel Safety: Multiple developers can trigger builds simultaneously without overwriting each other's work.

2. Health-Check Gated Deployment

The Logic: "Verify Before Trust"

Dependencies in a distributed system are fragile. We implemented a gated rollout where the frontend only deploys once the backend is proven functional.

# The Deployment Sequence
1. Deploy ad-server
2. POLL /health endpoint
3. IF 200 OK -> Proceed to deploy client-app
4. ELSE -> Fail build & Alert SRE

Operation details

The cloudbuild.yaml uses a bash polling loop that attempts to reach the service 30 times with 2-second intervals. This accommodates the "Cold Start" time of Cloud Run services.

3. Structural Implementation

The following snippet from our cloudbuild.yaml demonstrates the integration of these concepts:

# Health Polling Logic
for i in {1..30}; do
  HTTP_CODE=$$(curl -s -o /dev/null -w "%{http_code}" "$$SERVICE_URL/health")
  if [ "$$HTTP_CODE" = "200" ]; then
    echo "✅ Service is HEALTHY"
    exit 0
  fi
  sleep 2
done
