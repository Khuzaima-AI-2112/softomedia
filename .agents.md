## 2. ARCHITECTURE INVARIANTS

### 2.1 Single Source of Truth for API URL
- **ALL** frontend API calls MUST import `API_URL` from `client-app/src/config.js`.
- **NEVER** hardcode a backend URL string (e.g. `https://ad-server-*.run.app`) anywhere except `client-app/src/config.js`.
- If the backend URL changes after a deployment, update **only** `client-app/src/config.js`. No other file should need touching.

### 2.2 Monorepo Workspace Structure
- `ad-server/` — Express REST API, Firestore client, JWT auth, GCS integration.
- `client-app/` — React SPA (Vite), role-based routing, design tokens in `design-tokens.css`.
- Root `package.json` is the npm workspace host. Never install packages directly to the root; always target a workspace (`--workspace=ad-server` or `--workspace=client-app`).

### 2.3 Role Model (Three Personas — Do Not Add or Remove)
The system has exactly **three** user roles. Do not introduce new roles without explicit written confirmation from the project owner:

| Role | Entry Point | Key Privilege |
|---|---|---|
| `admin` | `/dashboard` | Full CRUD on all collections |
| `brand` | `/brand/dashboard` | Own campaigns & ad credits |
| `retailer` | `/retailer/dashboard` | Own screens & earnings |

Every new API route or Firestore rule MUST explicitly handle all three roles. A route that silently ignores a role will cause a broken user experience.

### 2.4 Authentication Architecture
- JWT tokens are issued by the `ad-server` using `JWT_SECRET` (env var, never hardcoded).
- Token payload: `{ uid, email, role }` — the `role` field drives all authorization decisions.
- Firestore security rules use `request.auth.token.role` — keep rules and JWT payload synchronized.
- `bootstrapAdmin()` on server start is **not** sufficient alone; the `/api/debug/seed` endpoint MUST also create the admin user as a safety net.
- The fallback `dev-secret-key-change-in-prod` in `index.js` MUST never reach production. The `JWT_SECRET` env var must always be set on the Cloud Run service before or at deploy time.

## 3. DEPLOYMENT RULES (CRITICAL — ZERO TOLERANCE)

### RULE D-1 · Atomic Deployments Only
```
✅ ONLY: gcloud builds submit --config cloudbuild.yaml .
❌ NEVER: manually delete, update, or replace individual Cloud Run services outside of the build pipeline
```
Bypassing `cloudbuild.yaml` breaks the CI pipeline and can leave frontend and backend versions mismatched.

### RULE D-2 · Seed Endpoint After Every Backend Deploy
After every successful `gcloud builds submit` for `ad-server`, immediately call:
```
GET https://ad-server-<hash>-uc.a.run.app/api/debug/seed
Expected response: { "status": "seeded" }
```
Cloud Run containers are ephemeral and restart frequently. `bootstrapAdmin()` alone cannot guarantee users exist.

### RULE D-3 · IAM Must Allow Public Invocation After Deploy
After any new Cloud Run service revision, verify:
```
gcloud run services get-iam-policy <SERVICE_NAME> --region us-central1
```
If `allUsers → roles/run.invoker` is missing, add it immediately. A missing IAM binding causes a 403 for all users.

### RULE D-4 · GCS Bucket Must Remain Publicly Readable
After any GCS bucket operation, verify public read access:
```
gcloud storage buckets add-iam-policy-binding gs://softo-media-live-ads/ \
  --member=allUsers --role=roles/storage.objectViewer
```
Without this, the screen player shows black screens (images return 403).

### RULE D-5 · Service Deletion Requires Explicit Verification
Before running `gcloud run services delete`:
1. Run `gcloud run services list` first.
2. Confirm the service URL matches the deletion target.
3. State the service name and URL and obtain **explicit user approval**.
4. Deleting a service deletes **ALL revisions** — this cannot be undone.

### RULE D-6 · Cache Invalidation After Image or API Changes
After deploying any image asset or API change, instruct the user to hard-refresh (Ctrl+Shift+R / Cmd+Shift+R). GCS Signed URLs cache for 60 minutes.

### RULE D-7 · Pre-Deployment Checklist (Must Run in Order)
1. `node verify_predeploy.js` (if present in repo root)
2. Grep all new/modified files for hardcoded `https://ad-server-*.run.app` or `https://client-app-*.run.app` — reject if found
3. Confirm GCS demo ad images are unique if assets were modified
4. Review `DEPLOYMENT_LOG.md` for known breakages that match current change

## 4. CODE RULES

### RULE C-1 · No Credentials or Secrets in Source Code
- Passwords (even demo passwords like `demo123` or `thisisbusiness`) must never be added to new production code paths. They exist in the seed/bootstrap for demo purposes only.
- `JWT_SECRET`, database credentials, and GCP service account keys must always come from environment variables or Secret Manager.
- The agent must scan any new file it writes for accidental secret injection before committing.

### RULE C-2 · Password Hashing Is Mandatory
- All passwords stored in Firestore MUST be hashed with `bcrypt` (salt rounds ≥ 10).
- Never store a plaintext password in any Firestore document. The `password` field name in seed data currently holds a hash — do not change this convention without migrating all documents.

### RULE C-3 · API Routes Must Apply Correct Rate Limiter
Every new Express route MUST be covered by one of the three existing rate limiters:

| Path Pattern | Limiter |
|---|---|
| `/api/auth/*` | `authLimiter` (strict) |
| Upload/create routes | `uploadLimiter` |
| Everything else | `generalLimiter` |

Never add a route that bypasses rate limiting.

### RULE C-4 · Firestore Access Is Backend-Only
- The React frontend must **never** access Firestore directly (no Firebase SDK in `client-app/`).
- All data operations go through the Express REST API in `ad-server/`.
- This keeps auth logic centralized and prevents client-side privilege escalation.

### RULE C-5 · CORS Is Explicitly Managed
- The backend uses `cors()` middleware globally. If origin restrictions are added, they must be configured in `ad-server/index.js` — never in individual route files.
- `cors.json` at the repo root governs the GCS bucket CORS policy. Update it and re-apply when adding new frontend origins.

### RULE C-6 · Debug Routes Must Not Exist in Production
- The `/api/debug/seed` endpoint is a **demo seeding mechanism only**. It creates users with known passwords.
- Before any customer-facing production launch, this route must be gated (e.g., behind an admin secret header or removed entirely).
- The agent must warn the user if it detects this route is still open when performing production deployment tasks.

### RULE C-7 · Component-Level API Calls Are Forbidden
- No React component (`*.jsx`) may call `fetch()` or `axios()` with a raw URL string.
- All API calls must go through a service module in `client-app/src/services/`.
- Service modules must import `API_URL` from `../config.js` (or relative equivalent).

### RULE C-8 · Design System Is Authoritative
- All colors, spacing, typography, and visual tokens are defined in `client-app/src/design-tokens.css`.
- New components must use CSS custom properties from `design-tokens.css`. Never introduce inline style hex codes or hardcoded pixel values for spacing.

## 5. DATA MODEL RULES

### RULE M-1 · Firestore Collection Ownership Fields Are Immutable
The following ownership fields must never be changed after document creation:

| Collection | Ownership Field |
|---|---|
| `users` | `email` |
| `locations` | `owner_id` |
| `screens` | `owner_id` |
| `advertisers` | `primary_contact_user_id` |
| `campaigns` | `advertiser_id` |
| `ads` | `advertiser_id` |
| `retailers` | `owner_user_id` |
| `brands` | `owner_user_id` |

An agent must never write a migration or update that reassigns these fields without explicit, confirmed user instruction.

### RULE M-2 · Signed URLs Cache for 60 Minutes
When generating GCS Signed URLs, assume a 60-minute cache window. Never display a cached URL as "fresh" to the user. Always regenerate when currency matters.

### RULE M-3 · Ad Duration Is 5 Seconds (Demo Default)
All demo ads use `duration_seconds: 5`. Do not change this default without also updating the player loop logic and the seed endpoint.

## 6. AGENT BEHAVIORAL RULES (ANTI-HALLUCINATION)

### RULE A-1 · Never Invent URLs
All service URLs must be read from `client-app/src/config.js`, `WHATS_AVAILABLE.md`, or confirmed live GCP output. Never fabricate a `*.run.app` URL.

### RULE A-2 · Never Assume a Deployment Succeeded
A deployment is only confirmed when:
1. `gcloud builds submit` exits with code 0, AND
2. The seed endpoint returns `{ "status": "seeded" }`, AND
3. The health endpoint returns `200 OK`.

Do not tell the user "the deployment succeeded" based only on a build submission.

### RULE A-3 · Never Delete or Overwrite Without Showing a Diff
Before overwriting any existing file in the repo, the agent must:
1. Show the current content (or a meaningful diff).
2. Explain exactly what will change and why.
3. Obtain explicit confirmation.

### RULE A-4 · Do Not Silently Fix the "Wrong" Problem
If the agent encounters an ambiguous error (e.g., login failure), it must enumerate the possible root causes (JWT_SECRET mismatch, IAM missing, seed not run, etc.) and ask the user which hypothesis to test first. Never pick one silently.

### RULE A-5 · Three-Role Coverage Check on Every Change
Before finalizing any change to authentication, routing, Firestore rules, or API endpoints, the agent must explicitly verify the change is correct for all three roles: `admin`, `brand`, `retailer`. State this check in its response.

### RULE A-6 · Reference Documents Are Authoritative Context
When answering questions about the system, consult these files in order of authority:
1. `.agents.md` (this file) — immutable rules
2. `.cursorrules` — operational deployment rules
3. `WHATS_AVAILABLE.md` — current feature status
4. `DEPLOYMENT_README.md` — deployment procedures
5. `DEPLOY_GUIDE.md` — extended deploy guide
6. Source code — ground truth for implementation details

Do not contradict these documents based on general knowledge alone.

### RULE A-7 · Credentials in Documents Are Demo-Only
The credentials visible in documentation (`sokallel@gmail.com / thisisbusiness`, `brand@demo.com / demo123`, `retailer@demo.com / demo123`) are **demo credentials for a seeded environment**. The agent must never present these as the user's production credentials or encourage using them in a live customer-facing deployment without changing them.
